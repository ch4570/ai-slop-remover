# 토스 디자인 사례를 제품 개선에 적용하기

토스 기술 블로그의 디자인 글을 요청받았거나, 아래 사례가 현재의 문구·입력·구조·상호작용 문제를 설명할 때 관련 절만 읽는다. 일반적인 개선은 [14가지 방법](anti-slop-methods.md)과 [공통 UI/UX 원칙](ux-foundations.md)을 사용한다.

공식 `toss.tech` 원문 8개를 2026-09-07에 확인했다. **관찰**은 글에서 저자가 설명한 내용이며 현재 토스 앱을 직접 검증했다는 뜻이 아니다. **적용·확인**은 이 프로젝트가 도출한 작업 지침이다. 원문 전체, 이미지, 코드를 복제하지 않았다.

## 1. Copy predicts the next action

출처: 김자유, [토스의 8가지 라이팅 원칙들](https://toss.tech/article/21022), 2022-11-15.

- **관찰:** 다음 화면을 예상할 수 있는 문구, 중복 설명 제거, 말로 읽어도 자연스러운 표현을 강조한다. 비용을 숨기거나 선택을 강요하는 문구를 경계한다.
- **적용:** CTA는 언젠가 얻을 혜택보다 지금 실행할 행동을 설명한다. 제목을 반복하는 부제를 줄이고, 중요한 조건과 결과는 남긴다. 기존 한국어 말투를 유지하며 소리 내어 읽어본다.
- **확인:** 버튼을 읽고 예상한 결과와 실제 handler가 일치하는지 확인한다. 예를 들어 신청서를 검토하는 단계라면 `신청 완료`보다 `신청 내용 확인`이 맞을 수 있다. 이 예시는 자체 작성한 조건부 문구다. 거절·나가기에도 과장된 손해나 죄책감을 붙이지 않는다.

토스의 해요체나 감정 표현을 모든 브랜드에 강제하지 않는다. 간결함을 글자 수 최소화로 평가하지 않는다.

## 2. Forms follow attention and input

출처: 정희연, [거꾸로 입력하는 가입 화면, 처음에 어떻게 떠올렸을까?](https://toss.tech/article/toss-signup-process), 2022-09-20.

- **관찰:** 실제 가입 흐름에서 키보드·추가 필드가 CTA와 선택란을 가렸고 입력 목적에 맞지 않는 키보드가 나타났다. 저자는 여러 구조와 순차 입력을 검토하고 사용성 테스트를 진행했다.
- **적용:** 정적인 폼 배치와 별도로 키보드가 열린 상태의 현재 입력, 다음 필수 입력, 제출 경로를 확인한다. 자동 포커스 이동은 완료 조건이 명확하고 수정 흐름을 해치지 않는 경우에만 선택한다.
- **확인:** 입력 시작 → 다음 필드 → 이전 값 수정 → 오류 수정 → 제출을 수행한다. 지원되는 IME 조합·붙여넣기·자동완성도 확인하고, 실제 OS 키보드와 합성 이벤트 검사를 구분한다. 구체적인 구현은 [입력 사례](interaction-recipes.md)를 따른다.

역순 폼, 자동 다음 필드 이동, 한 화면 한 입력을 보편 규칙으로 삼지 않는다.

## 3. Reordering includes non-drag operation

출처: 황수재, [드래그 앤 드롭은 사실 편한 UX가 아니다?](https://toss.tech/article/27752), 2024-05-30.

- **관찰:** 저자는 정밀한 드래그와 시각적 위치 변화에 의존하는 조작의 한계를 설명한다. 이동 버튼, 순서 낭독, 완료 후 초점 복귀를 함께 설계하고 기기별 차이를 확인했다.
- **적용:** 현재 구조에 맞는 올리기·내리기 버튼이나 목적지 선택을 제공한다. 이동 결과와 조작 상태를 전달하고, 항목의 안정적인 ID와 초점 경로를 유지한다.
- **확인:** 첫·중간·마지막 항목 이동, 경계 도달, 완료 후 위치와 초점을 확인한다. 터치 대체 조작, 키보드, 지원 스크린리더를 각각 검증한다.

원문의 과거 ARIA 설명·역할 우회 구현을 그대로 복사하지 않는다. 시맨틱과 키보드 구현은 현재 [웹](web.md)·[네이티브](native.md) 지침을 따른다.

## 4. Motion explains real work

출처: 박연주·김지혜, [인터랙션, 꼭 넣어야 해요?](https://toss.tech/article/interaction), 2023-09-07.

- **관찰:** 실제 상품을 보여주는 대출 심사 대기 화면을 소개한다. 저자는 이탈·결과 화면 도달 지표가 소폭 개선됐지만 대출 실행률에는 영향을 주지 못했다고 보고한다.
- **적용:** 움직임이 무엇을 이해시키는지 먼저 정하고, 실제 상태나 작업 정보를 표현한다. 보여줄 진행 정보가 없다면 알 수 없는 진행률이나 상품을 만들어내지 않는다. 정적인 상태 표시로 충분한지도 판단한다.
- **확인:** 대기 이유와 현재 상태가 이해되는지, 실패·중단·반복 입력·모션 감소에서도 조작과 피드백이 유지되는지 확인한다. [모션 지침](motion.md)을 사용한다.

다른 제품에서 같은 전환 효과를 약속하지 않는다. 토스의 내부 라이브러리나 특정 프로토타이핑 툴을 필수 의존성으로 만들지 않는다.

## 5. Platform context defines useful simplicity

출처: 이예슬, [누구나 리서치 하는 시대, UX리서처의 생존법](https://toss.tech/article/uxr-survival), 2025-11-27.

- **관찰:** 캘린더 개선에서 사용자가 정보를 발견하고 이해해 준비할 수 있는지를 기준으로 삼았다. PC 제품에서는 모바일의 간결함을 옮기는 것만으로 그 환경의 가치를 제공하지 못했다고 설명한다.
- **적용:** 리디자인의 성공을 사용자의 판단이나 완료할 작업으로 정의한다. 빠른 확인과 반복 비교·분석에 필요한 구조를 구분하고 [패턴 선택](pattern-selection.md)에 반영한다. 업무용 웹 화면의 필수 정보를 단순해 보이려고 숨기지 않는다.
- **확인:** 같은 내용과 과업으로 중요한 정보 발견 → 의미 이해 → 필요한 행동을 관찰한다. 소요 시간이나 성공률을 보고한다면 실제 관찰 조건을 기록한다. 모바일·PC의 역할을 화면 크기만으로 추정하지 않는다.

클릭·방문 증가만으로 사용자 가치가 개선됐다고 판단하지 않는다. 제품 전체 전략 검토를 작은 간격 수정에 끌어들이지 않는다.

## 6. Components support justified variation

출처: 김민수, [디자인 시스템 다시 생각해보기](https://toss.tech/article/44097), 2026-01-08.

- **관찰:** 시스템이 필요한 변형을 지원하지 못하면 컴포넌트 분리·코드 복제로 일관성과 업데이트 경로를 잃을 수 있다고 설명한다. 단순한 기본형과 조합 가능한 확장을 함께 제공한 사례를 소개한다.
- **적용:** 기존 토큰·컴포넌트에서 실제 요구를 만족시키는 확장 지점을 찾는다. 공통 상태와 동작을 유지하면서 필요한 변형만 표현하고, 반복되는 우회는 충족되지 않은 제품 요구인지 살핀다.
- **확인:** 기본형과 변형이 공통 의미·접근성·상태를 유지하는지 확인한다. 변경 이유와 영향을 받는 위치를 [디자인 기록](design-memory.md)에 연결한다.

모든 프로젝트에 Compound API를 도입하거나 TDS를 설치하라는 뜻이 아니다. 토스의 색상·글꼴·라운드 값을 기존 브랜드 위에 덮어쓰지 않는다.

## 7. Specifications communicate states in reading order

출처: 황희영, [제품이 커지면 디자인 시스템 가이드는 어떻게 개선돼야 할까?](https://toss.tech/article/toss-design-system-guide), 2024-04-05.

- **관찰:** 가이드의 읽는 순서가 모호해 생긴 구현 누락을 다룬다. 전체 구조에서 타입·내부 요소·상태로 이어지는 설명과 옵션을 함께 보여주는 사례를 사용했다.
- **적용:** 공통 컴포넌트를 크게 바꿀 때 정상 모습과 관련된 복잡한 조합을 기존 미리보기에서 확인한다. 실제 컴포넌트의 상태·큰 글자·지원 테마·접근성 조건을 읽는 순서대로 설명한다.
- **확인:** 문서에 정의한 구조와 동작을 실제 코드에서 찾을 수 있는지, 빠진 상태와 오래된 토큰이 없는지 확인한다. [컴포넌트 예시](../assets/component-specimen.md)를 재사용한다.

모든 옵션을 보여주는 명세 예시는 실제 제품 화면을 요소로 채우라는 뜻이 아니다. 작은 수정에 새 명세 사이트를 만들지 않는다.

## 8. Validate structure before polishing details

출처: 한지유, [업무용 툴, 내 동료가 정말 만족했나요?](https://toss.tech/article/tablecenter), 2024-07-24.

- **관찰:** 업무용 검색 도구에서 작업 시간과 만족도를 목표로 삼고 관찰에 따라 검색·필터·결과 순서를 개선했다. 복잡한 탐색은 거친 프로토타입으로 검증했으며 접힘 기본값도 관찰 후 바꿨다.
- **적용:** 구조가 불확실한 리디자인은 색·모션 마감 전에 실제 과업을 수행할 수 있는 작은 시안으로 확인한다. 기본 펼침·접힘과 정보 순서는 작업에 필요한 내용이 발견되는지로 결정한다.
- **확인:** 대표 과업의 완료 여부, 잘못 선택한 지점, 추가 설명이 필요했던 지점을 기록한다. 실제 사용자가 없으면 검토자의 예행연습으로 표시한다. 피드백 없이 만든 시안을 사용자 검증으로 부르지 않는다.

기존 미리보기와 승인된 테스트 데이터를 사용한다. 연구 참여자 수, 만족도, 개선 수치를 다른 제품의 기준이나 예상 성과로 가져오지 않는다.

## 적용 기록

필요한 경우 **현재 문제 → 채택한 판단 → 유지할 제약 → 실제 확인 결과**만 작업 기록에 남긴다. 원문의 사례를 현재 제품에서 관찰한 사실로 바꾸어 쓰지 않는다. 범위 밖의 연구·제품 전략·기능 구현을 이 문서만으로 시작하지 않는다.
