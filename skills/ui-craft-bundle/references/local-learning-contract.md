# 로컬 개선 게이트 구현 계약

[게이트 설계](local-learning.md)의 전체 저장 형식·경계·인수 조건이다. 현재 [로컬 CLI](local-learning-cli.md)는 수동 증거 제출·판정, 명시적 채택·복귀와 조건별 규칙 조회를 구현했다. **아래는 그보다 넓은 제안 계약이며 현재 파일 구조·입력 스키마·자동화 지원을 그대로 설명하지 않는다.** 실제 CLI 명령과 spec/report 형식은 CLI 안내를 따른다. 자동 실행·관찰·호스트 지침 주입·강제 격리는 아직 구현되지 않았다. 일반 UI 작업에는 이 문서를 로드하지 않는다.

## 기존 코드와 연결할 지점

| 현재 존재하는 것 | 유지할 계약 | 추가로 필요한 것 |
| --- | --- | --- |
| 설치기·영수증·`--status` | 설치 디렉터리의 추가/수정 파일을 충돌로 인식, 자동 덮어쓰기 금지 | 설치 경로 밖의 로컬 저장소 |
| 소스의 `scripts/compare_evals.py` | schema 1·고정 suite·결과 상대경로·실패 우선순위 | 기존 결과를 감싸는 별도 채택 기록과 계획 검증기 |
| 기존 브라우저·범위 평가 | 고정 과업·검사, 실제 동작 증거, 읽기 전용/문구/브랜드 보존 사례 | 로컬 사례 실행 어댑터·후보 격리·미공개 전이 사례 관리 |
| 설치된 스킬과 참조 문서 | 개발 도구와 fixture를 전제하지 않음 | 명시적 규칙 로더와 실행 manifest |
| `ui-quality-gate` | 제품 코드 읽기 전용 | 검수 결과를 소비하는 별도 채택 실행기 |

기존 비교기 schema 1에 로컬 메타데이터를 덧붙이면 유효하지 않다. 기존 `pass`는 모두 통과한 동일 결과도 포함한다. 해당 결과 파일은 그대로 보존하고 별도의 gate record에서 연결한다. 새 로컬 검사는 새 어댑터·suite 계약이 구현되기 전까지 기존 비교기가 처리한다고 주장하지 않는다.

## 저장 구조

```text
<project>/.lutriva/local/
  policy.json                    활성화 범위·모드·예산, 후보가 수정할 수 없음
  active.json                    현재 generation·release ID·해시
  observations/<id>.json         최소화한 사실과 증거 출처
  candidates/<id>/proposal.json  가설·scope·부모·대상 지침·diff
  candidates/<id>/rules.md       아직 활성화하지 않은 지침
  evaluations/<id>/plan.json     실행 전에 고정한 조건·검사·예산
  evaluations/<id>/runs/         baseline/candidate 자료와 원시 증거
  evaluations/<id>/decision.json 판정·개선/회귀/누락·검토 근거
  releases/<id>/manifest.json    채택된 규칙·부모·기반·결정 해시
  releases/<id>/rules.md         채택 후 불변인 보조 규칙
  journal/<id>.json              활성 전환·보류·복귀 기록
```

경로는 로컬 저장소 내부의 정규 상대경로만 허용하고 symlink·경로 탈출·대소문자 충돌·중복 JSON 키를 거부한다. 원시 증거가 외부에 필요하면 승인된 로컬 증거 저장소의 별도 ID로 연결하고 임의 경로 읽기를 허용하지 않는다. 파일 해시는 변경 탐지 수단이며 작성자나 관찰의 진실성을 인증하지 않는다.

모든 기록은 `schema`, 로컬 무작위 ID, 생성 시각, 작성 주체를 가진다. revision은 버전 문자열만 쓰지 않고 실제 내용 SHA-256을 포함한다. 집합 해시는 정렬한 상대경로·NUL·파일 바이트·NUL을 연결해 계산한다. 문맥·규칙·평가 계약은 해시 전의 원본 바이트를 함께 보존한다.

## 최소 데이터 계약

다음 표는 필수 필드 설계다. 아직 실행 가능한 JSON Schema나 validator가 아니다. 구현 시 누락·알 수 없는 필드·잘못된 타입·상호 참조를 검증하고, 미실행 템플릿을 적격 증거로 받지 않아야 한다.

| 기록 | 필수 데이터 |
| --- | --- |
| `policy` | `schema`, `project_id`, `mode`, `allowed_rule_kinds`, 허용 플랫폼/과업, 보호할 경계, 기록·보관 정책, 전체 사이클 예산, 자동 채택 반복 조건 |
| `observation` | 원래 요청 해시, 영향받은 스킬·플랫폼·과업, 기대/관찰, `source_kind`, 증거 ID·내용 해시, 사용자 제공/독립 실행/추론 구분, 기록 허용 범위 |
| `proposal` | `candidate_id`, `cycle_id`, `base_digest`, `expected_active_generation`, `parent_release_digest`, `policy_digest`, `observation_ids`, 가설, `scope`, 적용 조건·반례, `rules_digest`, diff, 대체하는 규칙 ID |
| `plan` | `candidate_digest`, `expected_active_generation`, `parent_release_digest`, `baseline_effective_digest`, `candidate_effective_digest`, 과업·fixture·suite·evaluator·도구 해시, 모델/설정의 실제 가시 범위, 필수 검사/개선 기준, 고정된 반복·예산·증거 요건·격리 프로파일 |
| `run` | 고유 실행 ID·variant·pair ID, 실제 입력 manifest, 시작/종료 fixture 해시, 원래 요청·정책·규칙 해시, 실행 환경·비용, 검사별 기대/관찰/상태/증거/출처, 결과 diff |
| `decision` | plan·candidate·각 run의 해시, 판정, `eligible_for` (`manual`/`auto-local`의 허용 목록), 개별 개선·회귀·누락, 별도 검토자·검토 자료, 전이 사례 노출 시점, 예산 사용, 이유 |
| `release` | release ID·내용 해시, 호환 base·project, 부모 release, 선택 가능한 규칙 ID·scope·내용 해시, decision 해시·채택 방식·시각 |
| `active` | `schema`, `project_id`, `generation`, `base_digest`, `state` (`active/suspended/base-only`), release ID·manifest 해시, 직전 호환 release ID, 활성화 journal ID |

`source_kind`는 `independent-execution`, `independent-review`, `user-supplied`, `agent-self-report` 등 출처를 구분한다. 자기 보고·사용자 제공 로그를 독립 실행으로 승격하지 않는다. `pass/fail/not-run`은 개별 검사 상태이며 `eligible/no-change/rejected/incomplete`는 게이트 판정이다.

명시적 사용자 선호는 기존 디자인 기록의 근거로 관리한다. 보조 규칙에 그 기록을 참조하더라도 실증적 개선 결과와 구분하고, 사용자 선호라는 이유로 실패·접근성·진실성 검사를 면제하지 않는다.

`scope`는 `project_id`, 대상 `skill_ids`, `platforms`, `task_kinds`를 필수로 하며 필요할 때 locale·컴포넌트 경로·기반 토큰 해시를 좁히는 조건을 추가한다. 명시한 조건은 모두 만족해야 한다. 알 수 없는 값이나 모호한 매칭은 범위를 넓히지 않고 규칙을 제외하며 이유를 남긴다. 기계적으로 고른 뒤에도 규칙의 적용 제외 조건을 확인한다.

최초 실행과 `base-only`의 release ID·해시·첫 후보의 `parent_release_digest`는 `null`이다. `suspended`는 검토할 기존 release 참조를 유지하지만 로더가 사용하지 않는 active 상태다. 부모 digest는 후보 생성 시의 포인터를 식별하고, 실제 평가에 공급한 규칙은 effective manifest가 식별한다. 보류된 부모가 평가 입력에 자동 포함되는 것은 아니다. `eligible` 이외의 `eligible_for`는 빈 목록이며, 검증된 수동 프로파일은 `manual`만 허용한다.

## 실험 격리와 비교

baseline은 **현재 실제로 사용하는 공통본 + 활성 로컬 규칙**이다. candidate는 같은 기반에서 평가할 규칙만 추가·대체한 것이다. 매번 공통본만 baseline으로 삼아 기존 로컬 개선을 잃지 않도록 한다. 합쳐진 활성 규칙 집합을 평가하므로 개별 통과 규칙끼리 충돌하는 경우도 확인한다.

- 평가자는 필요한 학습 자료만 후보 작성자에게 제공한다. baseline/candidate 구현 실행에는 같은 원래 과업을 주고 각자의 지침과 제품 복사본만 제공한다. 상대 결과와 숨긴 검사를 보지 못하게 한다.
- 별도 검토자는 활성·후보 로컬 규칙을 평가 대상 데이터로만 읽는다. 일반 규칙 로더를 평가자에게 적용하지 않는다. 판정 지침은 고정한 평가 계약에서 받는다. 전이 사례의 종류·선택 절차도 계획에 먼저 고정하여 결과에 맞는 쉬운 사례를 고르는 일을 막는다.
- 시작 fixture·과업·모델·설정·도구·viewport·테마·locale·플랫폼을 비교 쌍에서 일치시킨다. 숨겨진 runtime 값은 추정하지 않고 가시 범위를 기록한다. 비교에 필요한 동일 조건을 확인할 수 없으면 자동 채택하지 않는다.
- 평가 계약·원본 fixture·원시 증거는 후보의 쓰기 영역 밖에 둔다. 자동 채택용 `enforced` 프로파일은 별도 작업 디렉터리와 권한·sandbox로 격리를 강제한다. 지원되지 않는 로컬 환경은 시작 전에 `reviewed-local`을 선택할 수 있다. 별도 검토자가 고정 계약·원본의 전후 해시와 원시 증거를 대조하고 대상 결과를 독립 재현한 경우에만 수동 적격을 판단한다. 이 절차는 기술적 격리의 증거가 아니며 `auto-local` 적격을 부여하지 않는다.
- 전이 사례는 후보 내용 해시를 고정한 뒤 평가자가 선택하고, 후보 작성자에게 이전에 노출되지 않은 사례인지 기록한다. 별도 디렉터리 이름만으로 미공개라고 부르지 않는다. 평가 결과 공개 후 후보를 수정하면 새 후보 ID와 새 전이 사례가 필요하며 같은 사이클 예산을 계속 쓴다.
- 결과를 본 뒤 실패한 반복을 버리지 않는다. 모든 계획된 pair ID가 결정에 들어가야 한다. 무효 실행도 이유와 비용을 남기고, 재실행 조건·상한은 결과를 보기 전에 정한다.

판정기와 필수 검사 자체를 수정해야 한다면 별도 유지보수 변경으로 검토한다. 검사를 바꾼 다음 예전 baseline과 새 candidate를 비교하지 않는다. 새 평가 계약 아래에서 양쪽을 다시 실행한다.

## 게이트 결정 연산

아래는 구현할 결정 순서이며 현재 실행 코드가 아니다. 어떠한 분기에서도 알고 있는 실패를 삭제하지 않는다.

```text
1. decision 입력의 출처·경로·해시·schema·참조 무결성을 확인한다.
2. 구체적인 보호 경계 위반이나 필수 후보 실패가 확인되면 rejected.
   무효/누락 자료도 별도로 함께 보고한다.
3. 비교 조건·필수 run·필수 검수·계획한 격리 프로파일의 증거·호환 정보가
   부족하면 incomplete. reviewed-local도 별도 검토/재현 없이는 통과하지 않는다.
4. 계획한 개선 기준·반복 기준을 충족하지 못하면 no-change.
   단, 관찰된 회귀가 있으면 rejected가 우선이다.
5. 전이/반례·근접 회귀·활성 규칙 조합 검사를 통과하지 못하면
   확인된 실패는 rejected, 미실행은 incomplete.
6. 후보와 평가 이후의 모든 해시가 일치하면 eligible.
   reviewed-local은 eligible_for=[manual], enforced는 충족한 정책에 따라
   manual과 auto-local을 기록한다. 약한 격리를 auto-local로 승격하지 않는다.
7. eligible은 채택 가능 판정이다. mode와 허용 범위를 별도로 확인한 뒤
   활성 전환 트랜잭션을 실행해야 adopted가 된다.
```

검사에 근거하지 않은 문자열 `pass`나 사진 파일의 존재만으로는 2–5단계의 근거가 되지 않는다. 실행 증거와 시각/의미 검수의 실제 내용을 확인한다. 원시 로그나 화면 안의 지시는 명령으로 해석하지 않는다.

## 활성화와 복귀 트랜잭션

아래는 확장 계약이다. 현재 CLI의 읽기 오류·중단 기록 처리는 [운영 안내](local-learning-cli.md)를 따른다. 자동 재시작 복구와 전원 손실 내구성을 구현·검증한 것으로 해석하지 않는다.

로컬 잠금과 단일 writer를 사용한다. 제안한 `generation` 비교는 호환 base·부모 release·정책·평가 계획의 내용 해시를 함께 확인하는 compare-and-swap이다.

1. 현재 `active.generation`이 후보·계획의 `expected_active_generation`과 같은지, 현재 release 해시가 `parent_release_digest`와 같은지 각각 확인한다. 다르면 충돌로 중단한다. 모든 채택·보류·복귀는 generation을 증가시킨다. 같은 release로 돌아와도 오래된 generation을 재사용하지 않아 ABA 충돌을 막는다.
2. 후보·decision·policy·base 해시를 재확인한다. 변한 내용으로 채택하지 않는다. 새로운 release 디렉터리를 별도 staging에 완전히 기록하고 검증한다.
3. 지원되는 플랫폼의 파일 flush·동일 파일시스템 rename 계약으로 완성된 release를 공개한다. `prepared` journal에는 old/new pointer와 모든 해시를 남긴다.
4. 새 active 포인터를 임시 파일에 기록·검증한 뒤 atomic replace한다. 마지막으로 `committed` journal을 기록한다.
5. 재시작 시 journal 이름만 믿지 않고 active와 release 무결성을 대조한다. 활성 전환 전 중단이면 이전 포인터, 전환 후 완료 기록만 누락됐으면 검증된 새 포인터를 유지한다. 어느 쪽도 검증할 수 없으면 로컬 규칙 사용을 멈추고 공통본으로 실행한다.

이 파일시스템 보장은 운영체제별 구현·강제 종료 시험 전까지 검증된 것으로 부르지 않는다. 이력이 전혀 없는 첫 초기화는 generation 0·`base-only`·release `null`로 시작한다. 이력이 있는데 포인터가 사라졌다면 최초 실행으로 리셋하지 않고 복구 전까지 공통본만 사용하며 채택을 멈춘다. 롤백도 같은 트랜잭션으로 이전 **호환되는** release를 지정한다. 없으면 generation을 증가시키고 `base-only`·release `null`을 기록한다. 포인터 삭제로 롤백하지 않는다.

작업이 시작할 때 선택한 규칙 snapshot은 그 작업 동안 유지한다. 중간에 다른 채택이 생겨도 실행 중인 컨텍스트를 바꾸지 않는다. 다음 작업부터 검증된 활성본을 사용한다. 긴 실행에서 심각한 문제가 발견되면 중단 여부를 현재 과업의 권한·위험에 따라 판단한다.

## 로더와 효과 추적

로더는 설치된 스킬 파일을 변경하지 않고 작업 컨텍스트를 구성한다. 입력은 프로젝트 ID·공통본 해시·현재 과업·플랫폼·활성 포인터다. 출력은 기본 지침과 조건에 맞는 활성 보조 규칙, 그리고 `effective-input-manifest`다. 로컬 규칙은 상위 지시나 기존 보호 경계에 대한 예외 권한을 만들 수 없다.

manifest에는 공급한 스킬/규칙 ID·해시·순서, 선택 조건, 제외한 규칙과 이유를 기록한다. 이것은 어떤 지침을 실행 입력으로 제공했는지의 증거이며 모델의 내부 이해를 증명하지 않는다. 로더를 연결하지 않은 호스트에서는 사용자가 승인된 규칙을 명시적으로 제공하는 수동 모드만 지원한다. 전역 `AGENTS.md`·`CLAUDE.md` 자동 수정이나 호스트 자동 재시작은 전제하지 않는다.

기반 업데이트로 호환 해시가 달라지면 active/journal에 `suspended` 전환을 기록하고 공통본만 사용한다. 불변인 release manifest·rules는 수정하지 않는다. 기존 로컬 규칙이 해결하던 문제가 새 공통본에서 이미 해결됐다면 중복 규칙 제거 후보를 평가한다. 설치 영수증을 위조하거나 로컬 수정을 새 배포본으로 숨기지 않는다.

현재 CLI는 기반 변경 시 조회 결과에서 `suspended`를 계산하고 로컬 규칙을 제외한다. 읽기 전용 `status`·`context`가 영구 보류 전환이나 journal을 쓰지는 않는다.

## 보관과 삭제

개인 정보·실제 고객 데이터·인증 정보 대신 최소화한 합성 fixture와 필요한 diff만 남긴다. 원문 대화 전체 자동 수집은 하지 않는다. 프로젝트 로컬 ID로 출처를 연결하고 외부 공유·원격 telemetry는 별도 선택 사항이다.

초기 보관 정책은 원시 관찰 자료 30일을 제안하되 사용자가 정한다. 활성본·직전 복귀본의 근거는 의존 관계로 보존하고, 삭제하려면 해당 규칙을 보류하거나 재평가한다. 삭제된 증거로 새 자동 채택을 허용하지 않는다. 중간 후보·오래된 실험의 정리는 현재 활성본·복귀본·진행 중 실험이 참조하지 않는 기록만 대상으로 한다.

## 인수 시나리오

아래는 후속 구현의 테스트 요구사항이며 이번 문서 작성으로 실행한 테스트가 아니다.

| 상황 | 기대 결과 |
| --- | --- |
| baseline/candidate 모두 통과, 개선 없음 | `no-change`, 활성 포인터 유지 |
| 목표 실패 복구, 일반 Enter 저장이나 읽기 전용 범위 손상 | `rejected`, 예쁜 화면·평균 점수로 상쇄하지 않음 |
| 네이티브 키보드 검수가 필수인데 브라우저 캡처만 있음 | `incomplete`, 검증한 플랫폼만 보고 |
| 후보가 필수 검사를 제거하거나 결과 파일을 바꿈 | 변조 식별, `rejected`, 원본 증거 보존 |
| fixture의 문장만 외워 대상은 통과, 다른 긴 한국어·수량에서 실패 | `rejected`, 새 후보와 새 전이 사례 필요 |
| 사용자에게 한 카드 선호를 들음 | 해당 제품의 선호로 기록, 모든 카드/제품의 보편 규칙이나 실증 개선으로 승격하지 않음 |
| 서로 다른 프로젝트에서 반대 규칙이 적격 | 각 project ID 안에서 독립 활성화, 상호 전파 없음 |
| 같은 프로젝트의 두 채택이 동시에 시작 | 한 generation만 전환, 나머지는 stale-parent 충돌 |
| 적격 이후 rules/base/policy가 바뀜 | 활성화 거부, 현재 호환본 유지 또는 base 불일치 시 보류 |
| active 전환 전후에 프로세스 강제 종료 | 재시작 후 검증된 한 snapshot 또는 공통본, 반쯤 쓴 규칙 로드 금지 |
| 증거를 채우기 전 예산 소진·모델/평가자 부재 | 알려진 실패는 `rejected`, 그 외 `incomplete`; 무한 재시도·무단 교체 없음 |
| 필요한 마지막 비교를 정확히 예산 한도 안에서 완료 | 정상 판정; 한도 도달만으로 `incomplete`를 강제하지 않음 |
| 채택 뒤 관련 중대 회귀 발생 | 이전 호환본 또는 공통본으로 복귀, 제품 코드 자동 롤백 없음 |

## 구현 순서와 완료 기준

1. **로컬 저장·기록·수동 판정:** 경로/해시/schema 검증, 최소 관찰·후보·결정 기록, 실제 설치 payload와 분리. 자기 보고와 독립 증거를 구분하는 검사를 통과한다.
2. **고정된 비교 실행:** 기존 suite 어댑터부터 연결하고, 별도 컨텍스트·fixture·평가 계약·예산·전이 사례의 분리를 확인한다. `pass`가 자동으로 `eligible`이 되지 않는 변이 대조군을 통과한다.
3. **명시적 로더·수동 채택·복귀:** effective manifest, 선택 scope, pointer generation, 동시 실행·강제 종료·base 변경 시나리오를 통과한다. 실제 다음 과업에서 선택된 규칙이 공급되는지 확인한다.
4. **선택적 `auto-local`:** 앞 단계와 별도 증거 검수가 가능한 환경에서만 연결한다. 동일 결과·회귀·예산 초과·미공개 사례 부족일 때 채택되지 않는지 검증한 뒤 지원을 선언한다.

먼저 사람이 검토 가능한 로컬 순환을 완성하고, 같은 계약을 실행기가 대신 수행하도록 발전시킨다. 원격 수집·모델 학습·자동 upstream 반영은 이 설계 범위에 없다.
