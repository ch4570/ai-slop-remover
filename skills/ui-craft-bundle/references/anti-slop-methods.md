# Methods for removing generic UI

Use this when an audit or redesign needs a concrete intervention. Select methods from observed friction in the requested surface; this is a toolbox, not a sequence or a finding quota. For accessibility thresholds and shared interaction principles, use [UX foundations](ux-foundations.md). “AI slop” describes a result, not evidence of its author.

## Identify what should change

Start with a real task and representative content: who is doing what, with which object, and how they know it worked. Record the current obstacle and a checkable outcome. For example, “compare delivery dates and totals without opening every order” gives a better direction than “make this premium.” If only source or a screenshot is available, distinguish observations from hypotheses about behavior.

The methods below are Lutriva's design synthesis. The linked research explains relevant principles; it does not establish that any color, font, component, or generated screen is inherently poor.

For concrete Korean product examples, [Toss design cases](toss-design.md) connect these methods to predictable labels, keyboard-aware forms, non-drag reordering, meaningful motion, platform context, component variation, and early task validation. Read only the case that explains the current obstacle.

## Structure and visual meaning

| Method and useful symptom | Scoped intervention | Preserve / recheck |
| --- | --- | --- |
| **1. Put the task in the foreground.** A welcome hero, metric strip, or introductory panel displaces daily work. | Give the working object and its controls priority. Keep explanatory content where it changes a decision; remove unsupported filler within scope. | Marketing, onboarding, and unfamiliar tasks may need explanation. Verify users can identify the object and next action without losing necessary context. |
| **2. Replace repeated shells with a task-shaped structure.** Identical cards separate fields users must compare. | Inspect actual comparison fields; try aligned rows/table, list-detail, timeline, or a reading surface using [pattern selection](pattern-selection.md). | Cards suit independent objects and browsing. Retain IDs, units, sort/filter/selection, and actions; check both comparison and narrow-screen access. |
| **3. Group by meaning.** Nested borders, backgrounds, and gaps imply relationships that the data does not have. | Use proximity and alignment for simple groups; retain a container when it communicates a real object, boundary, or shared action. Keep metadata with its owner. | Removing all containers can destroy grouping. Check whether each label, status, and action still clearly belongs to the right object. |
| **4. Assign emphasis by consequence.** Several unrelated buttons, badges, and headings compete equally. | Use existing primary/secondary/text roles within each action group; reduce decorative emphasis before reducing necessary text contrast. | Independent tasks may each need an action. There is no universal one-button-per-screen rule. Keep warning severity and interactive affordances recognizable. |
| **5. Give typography and spacing semantic roles.** Giant titles coexist with tiny useful data; arbitrary sizes or gaps change between similar sections. | Reuse a small set of existing heading, body, label, and metadata roles. Allocate space to reading and grouping, and align comparable values with units. | Preserve brand fonts and intentional density differences. Inspect long content and text scaling; do not fix overflow by shrinking text or hiding it globally. |
| **6. Make specificity come from the product.** The screen could be relabeled as another domain without changing its contents. | Use actual object relationships, useful statuses, units, vocabulary, and available assets. Carry a justified visual characteristic through existing tokens. | Familiar UI can be appropriate. Do not manufacture charts, testimonials, customer counts, imagery, asymmetry, or an alternate beige/serif preset to seem distinctive. |

Grouping follows [NN/G's common-region principle](https://www.nngroup.com/articles/common-region/); emphasis follows its [visual-hierarchy guidance](https://www.nngroup.com/articles/visual-hierarchy-ux-definition/). The interventions and checks are applications to this workflow, not numerical design laws. Continue with [art direction](art-direction.md) when the broader visual direction needs a decision.

## Interaction and content

| Method and useful symptom | Scoped intervention | Preserve / recheck |
| --- | --- | --- |
| **7. Disclose complexity at the right point.** Rare options crowd frequent work, or a minimal surface hides everything. | Keep common actions and relevant current choices visible; put genuinely secondary options behind a labeled disclosure when it helps. | Do not conceal active filters, errors, costs, consequences, or required fields. Open and close the disclosure; verify current settings remain understandable. |
| **8. Make controls recognizable.** Icon-only, hover-only, or drag-only actions require guessing. | Use familiar platform controls, labels for ambiguous actions, visible focus and selection, and equivalent input paths. | Keep accessible names, roles, state, and adequate hit areas. Check touch, keyboard, and assistive access relevant to the platform using [UX foundations](ux-foundations.md). |
| **9. Put feedback beside its cause.** A disappearing toast is the only evidence of an error or a completed action. | Show useful persistent state with the affected object or field; reserve broader notices for broader events. Trace the result with [interaction recipes](interaction-recipes.md). | Do not announce success before the promised state change. Check failure, retry, retained input, and whether the message is available without moving focus unnecessarily. |
| **10. Reduce memory and re-entry.** Users reopen objects to remember values, repeat known information, or restart after a mistake. | Keep relevant selections, comparison attributes, constraints, and entered values available. Offer edit, Back, cancel, or undo where the existing operation supports them. | Respect privacy and the actual draft lifetime. Do not invent durable storage or undo. Revisit a prior step and check changed dependent values and recovery. |
| **11. Replace generic copy with state-specific meaning.** “Get started,” “Something went wrong,” or “All done” obscures the next step. | Derive verbs, labels, help, and recovery text from real handlers and domain vocabulary. Distinguish first use, no matches, loading, and permission limits. | Preserve localization, interpolation, and accessible names. For example, “검색어를 바꿔 다시 검색해 주세요” fits only a no-match state with an available search control. |
| **12. Adapt the task across available space.** Desktop is merely shrunk, or mobile hides actions to look tidy. | Prioritize content and change layout when it stops fitting. Preserve the selected object when moving from adjacent list-detail to separate screens. | Keep secondary actions reachable; inspect keyboard-open layout, safe areas, supported large text, and return position. A wide comparison table may need deliberate local scrolling. |
| **13. Remove performative motion and waiting.** Entry choreography, parallax, or fake loading delays postpone useful work. | Keep feedback immediate and animate only a meaningful change in state or spatial relationship. Use [motion guidance](motion.md) for changed transitions. | Preserve clear static feedback and reduced-motion behavior. Exercise interrupted or repeated input; do not make every control animate to meet a polish quota. |
| **14. Stress the design with real variation.** The polished sample works only for three short items in the happy state. | Use realistic long/localized labels, missing values, many records, pending, empty, error, and selected/focused states that affect the change. | Keep synthetic data labeled and the existing brand. Use an existing [component specimen](../assets/component-specimen.md) for shared changes; do not add a preview framework for a local edit. |

Disclosure is informed by [NN/G's progressive-disclosure guidance](https://www.nngroup.com/articles/progressive-disclosure/); visible context and recovery by [Jakob Nielsen's usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/). [GOV.UK notification guidance](https://design-system.service.gov.uk/components/notification-banner/) supports placing task-related messages in context, and its [check-answers pattern](https://design-system.service.gov.uk/patterns/check-answers/) supports reviewing and editing entered information. Transfer those decisions where useful; do not impose GOV.UK page templates on every product.

## Apply, compare, retain

- For a narrow fix, apply the relevant method directly. For an unresolved structural redesign, compare plausible structures using the same task and content; do not generate cosmetic variants unless requested.
- Preserve useful reference decisions rather than copying another product's page shell. Inspect references before claiming to use them, and connect reusable changes to [design memory](design-memory.md).
- Recheck the original obstacle with comparable content, state, and viewport. Record which result changed and which tradeoff remains. A design hypothesis about faster scanning is not measured user performance.
- Stop when material scoped findings are resolved. Do not count removed cards, added whitespace, clicks, or animations as quality scores. Follow [verification](verification.md); appearance alone cannot establish usability or accessibility.

Sources reviewed 2026-09-07. These methods are optional interventions selected by task evidence; platform requirements retain their own scope and exceptions.
