# PR 작성 가이드

**`Summary → Changes → Test plan`**을 모든 PR의 기본 순서로 사용합니다. 제목과 본문은 짧고 구체적으로 쓰며, 본문은 한국어로 작성합니다. [GitHub 템플릿](../.github/PULL_REQUEST_TEMPLATE.md)과 CLI로 만든 PR에 같은 기준을 적용합니다. 사용자가 명시한 형식과 범위가 우선합니다.

공개 자료의 구조와 검증 관례를 참고해 이 저장소용 문구를 작성했습니다. 상위 프로젝트의 본문·코드·봇 서명은 복사하지 않았습니다. 다른 저장소의 `dev` 브랜치 규칙, 전용 검사 명령, 특정 실행기의 성능 수치를 가져오지 않습니다. Lutriva의 기본 대상 브랜치는 `main`입니다.

## 제목과 본문

제목은 `type: 변경 결과` 형식입니다. `feat`, `fix`, `docs`, `test`, `refactor`, `chore` 중 실제 변경에 맞는 유형을 사용하고, 필요하면 범위를 괄호로 붙입니다. 예: `fix(learning): 오래된 평가의 재채택 차단`. 가능하면 72자 이내로 작성하되 의미를 자르지 않습니다. `개선`, `업데이트`, `수정 사항`처럼 결과를 알 수 없는 제목은 피합니다. 설계만 바뀌면 `docs`로 드러냅니다.

| 섹션 | 작성 기준 |
| --- | --- |
| `Summary` | 사용자 문제와 달라진 결과를 1–3개 항목으로 설명. 버그면 발생 조건과 이전·이후 동작 포함. |
| `Changes` | 결과를 만드는 핵심 변경과 이유. 작은 PR은 한 항목, 여러 영역이면 관련 변경끼리 묶음. |
| `Test plan` | 실행한 정확한 명령·시나리오, 관찰 결과, 필요한 환경·근거 링크를 체크 항목에 함께 기록. |
| `Review notes` | 선택. 호환성, 적용 조건, 미검증 범위, 복귀 방법 중 리뷰 판단에 필요한 내용만 기재. |

관련 이슈가 있으면 본문 끝에 `Fixes #123` 또는 `Refs #123`을 적습니다. 없으면 생략합니다. 화면 변경은 `Changes`에 전후 캡처와 화면 조건을 붙이고, 긴 로그는 CI나 검증 기록으로 연결합니다. 매번 빈 이슈 칸·고정 명령 표·해당 없는 체크리스트를 남기지 않습니다.

## 검증 결과를 쓰는 법

- `[x]`는 실제로 통과한 검사입니다. 필요한 검사가 미실행·실패 상태라면 `[ ]`와 이유·영향을 씁니다. 실행 예정인 명령을 완료 표시하지 않습니다.
- 일부 테스트만 실행했다면 전체 suite 이름으로 줄여 쓰지 않습니다. 수정 후에는 영향을 받는 검사를 재실행하고 최종 결과를 기록합니다.
- 로컬 검사, 원격 CI, 실제 화면·에이전트 비교는 각각 구분합니다. CI는 PR의 현재 head 커밋과 연결된 결과를 확인합니다.
- 스킬·성능 향상을 주장하면 기준과 후보, 동일 조건, 반복 수, 회귀·전이 결과를 적습니다. 두 결과가 모두 통과한 사실은 개선의 증거가 아닙니다.
- 스키마·해시·도구 테스트 통과로 UI 품질, 증거의 진실성, 미실행 플랫폼까지 검증했다고 표현하지 않습니다.

아래는 **형식을 보여 주는 가상의 버그 수정 PR**입니다. 검사 결과는 실제 PR에 복사하지 않습니다.

```markdown
## Summary

- 저장 실패 후 재시도하면 작성 중인 초안이 사라지는 문제를 수정합니다.

## Changes

- 실패한 응답에서 초안을 보존하고, 저장 성공 이후에만 편집 상태를 초기화합니다.

## Test plan

- [x] 저장 실패 → 내용 수정 → 재시도 시나리오: 수정 전 초안 소실, 수정 후 보존.
- [x] 정상 저장 회귀 검사: 저장한 값과 다시 불러온 값 일치.
- [ ] 실제 모바일 기기 검수: 기기 환경이 없어 미실행.
```

## PR 생성과 수정

최종 diff와 검증 결과를 확인한 뒤 완성한 본문을 UTF-8 임시 파일에 저장합니다. 주석·빈 항목을 제거하고 기본 세 섹션의 순서와 실제 줄바꿈을 확인합니다. CLI에는 본문 파일을 `--body-file`로 전달합니다. 범위나 head 커밋이 바뀌면 제목·본문·검증 링크도 최종 상태에 맞춥니다.

```sh
# pr_body_file은 검토한 본문 파일의 경로입니다.
gh pr create --base main --title 'feat: 구체적인 변경 결과' --body-file "$pr_body_file"
# 기존 PR을 갱신할 때 pr_number에는 실제 PR 번호를 지정합니다.
gh pr edit "$pr_number" --body-file "$pr_body_file"
```

PR 생성 요청은 브랜치·커밋·push·PR 게시와 연결된 검증까지 수행하는 범위로 해석합니다. 템플릿만 요청받으면 템플릿을 작성하며, PR 생성 요청이 없는 상태에서 게시하지 않습니다. PR 생성과 병합·릴리스 게시는 별개입니다.
