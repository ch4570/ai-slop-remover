반복 집계하지 않았으며, 이번에는 실행 도구와 회귀 테스트를 직접 개선했다.

## 재현한 문제와 수정

| 문제 | 수정 전 실제 결과 | 수정과 재검증 |
| --- | --- | --- |
| 일반 파일이 아닌 `manifest.json`을 읽음 | 작성자 없는 FIFO에서 목록·상태·dry-run·실제 설치가 대기; 테스트가 각 자식을 2초 후 종료·회수 | JSON을 열기 전 `lstat`으로 일반 파일 확인. 네 모드 모두 오류로 즉시 거부, 내용·mtime·목적지 보존 |
| ZIP 형식 범위 밖의 원본 파일 시각 | 배포 해시·스킬·정적 계약 검증 후에도 1980년 이전 시각은 오류, 2107년 이후는 `struct.error` traceback | `strict_timestamps=False`로 ZIP 메타데이터만 허용 범위로 보정. 두 경계 모두 내보내기·검증·실제 설치 통과 |

설치기는 기존 심볼릭 링크 거부를 유지하고 FIFO를 읽기 전에 거부한다.
테스트의 파일 스냅샷도 특수 파일을 열지 않고 종류·모드·mtime를 기록하도록
바꿨다. 디렉터리 manifest는 원래도 거부됐으며 새 테스트의 네 실패는 구체적인
진단 문구를 요구한 결과다. 수정 전 총 여덟 실패를 여덟 멈춤 결함으로 세지 않는다.

ZIP의 정상·두 날짜 경계 테스트는 실제 배포 파일을 임시 경로에 복사하고 실제
CLI를 실행한다. CRC, 중복 없는 정확한76개 파일 집합, 원문·SHA를 확인한 뒤
새 경로에 풀어 가상 프로젝트에 설치하고 모든 스킬 바이트를 대조한다. 원본
내용·수정 시각은 그대로이며 상한 시각은 ZIP의 2초 단위 저장 규칙까지 확인한다.
기존 출력 파일을 덮어쓰지 않는 동작과 손상된 배포 파일을 출력 디렉터리 생성
전에 거부하는 동작도 유지했다. 원본 수정 시각을 실제 저장소에서 바꾸지 않았다.

`install.py`, `scripts/export_bundle.py`, 기존 설치 테스트, 새
`tests/test_export_bundle.py`를 변경했다. `CHANGELOG.md`에 미배포 변경을
추가하고 manifest를 갱신했다. 배포 경로75개는 같고 변경된 배포 해시는 설치기와
변경 이력 두 개뿐이다. 스킬 파일65개·버전2.4.0·의존성·CLI 인자는 그대로다.

## 실제 검증

- 수정 전 `python3 -B -m unittest discover -s tests -p test_export_bundle.py -v`: 다섯 검사 중 날짜 경계 두 개 실패, 나머지 세 개 통과. 수정 후 다섯 개 통과.
- 설치기 신규 두 메서드: 수정 전 FIFO 네 모드 대기와 디렉터리 진단 네 실패를 보존. 수정 후 두 메서드·여덟 모드 통과. 작성자의 별도 기존 설치 검사81개 통과도 보충 자료로 남겼다.
- 최종 변경 이력·manifest 갱신 후 `python3 -B -m unittest discover -s tests -q`: Python3.9.6에서300개 실행, 253개 통과·47개 건너뜀, 종료0. 이번에는 opt-in 브라우저 검사를 활성화하지 않았다.
- `npm test`:24개 통과, 종료0. 실제 npm tarball 파일 집합·설치·두 CLI 별칭·상태 보고 검사를 포함한다.
- Python3.12.14에서 새 export 전체와 FIFO/디렉터리 두 메서드를 함께 실행:7개 통과, 종료0.
- `npm run check`, `npm run check:js`: 배포 해시·7개 스킬·24개 정적 계약·참조/의존성·Python/JavaScript 구문 검사 통과. 정적 계약을 에이전트 실행으로 세지 않는다.

원시 명령 기록은 실행 파일·인자·cwd·시작/종료 시각·종료값과 stdout/stderr를
보존한다. 변경 이력만 추가하기 전의 전체 Python 검사와 export3.12 검사도
별도로 남겼으며 최종 실행에 합산하지 않는다. [독립 검토](cycle-12-review.md)는
실제 Python3.9 표준 라이브러리, 구현·테스트와 실패/통과 출력을 읽고 수정이
필요한 문제를 찾지 못했다. 검토자는 통합 검사를 중복 실행하지 않았으며,
이후 변경 이력·manifest 검증은 부모의 별도 결과다.

## 적용 조건과 보존 범위

FIFO 회귀는 `os.mkfifo`가 없는 환경에서는 건너뛴다. 실제 검증 환경은 macOS이며
Windows/Linux CI, 동시 파일 교체 경쟁을 방어한다고 주장하지 않는다. 없는
manifest에 대한 CLI 오류는 기존 OSError 처리로 종료1을 유지한다. 직접
`load_bundle`을 호출하면 이전의 포장된 BundleError 대신 OSError가 전달되는
차이는 검토에 명시했다. 해당 예외 종류를 보장하는 공개 계약은 발견하지 못했다.

시각 보정은 ZIP 메타데이터만 바꾸며 재현 가능한 빌드 전체를 보장하지 않는다.
다른 I/O 실패 시 새 출력에 부분 ZIP이 남을 수 있는 기존 동작은 이번 범위에서
바꾸지 않았다. 최초 재현의 부분 ZIP도 성공한 배포물로 취급하지 않고 보존했다.
사용자 파일·전역 설정·실제 호스트 설치·외부 서비스·브라우저·의존성·원격 저장소는
변경하지 않았다. 테스트 설치와 자식 종료는 소유한 임시 가상 환경에만 한정했다.

[증거 압축](cycle-12.tar.gz), [파일별 목록](cycle-12-inventory.json)에
원본 배포 복사본, 최종 변경 파일, 실패 재현 코드, 부모 명령 원문, 설치기
red/green 출력, 독립 검토를 보존했다. 작성자81검사 자료는 실제 마지막 출력
조각이며 전체 전사본으로 꾸미지 않았다. FIFO를 포함한 가상 트리는 압축하지
않고 선택한 일반 파일만 보존했다. 추가 비압축 staging 없이137개 일반 파일·
3,254,056바이트의 집합·내용·모드·mtime를 전후 확인했다. 압축은2,757,640바이트,
SHA-256은 `12272ef629f6a8cfa2cf6ef642360790a833e67b632ac6e16996d2fb3fcdf39b`다.
압축을 새 경로에서 다시 실행하지는 않았다. 테스트 중 ZIP 해제·설치와 보존용
tar의 재실행은 다른 주장이다. 밤샘 피드백 목표는 계속 진행한다.

보존 압축 추가 후 `python3 scripts/check_evidence_archive.py`에 이 사이클의
inventory와 tar를 전달해137개 파일 집합·크기·SHA 일치와 종료0을 확인했다.
`npm run check`와 이 디렉터리의 `shasum -a 256 -c SHA256SUMS`도 종료0이었다.
기존11개와 새 압축의 무결성 재확인은 추가 행동 커버리지로 세지 않는다.
[생성·최종 검사 명령 원문](cycle-12-archive-build.json)은 검증 대상 tar 밖에
별도로 남겼다. 최종 staged `git diff --cached --check`도 통과했다.
