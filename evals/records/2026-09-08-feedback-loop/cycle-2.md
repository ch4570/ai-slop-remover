# 두 번째 피드백 사이클

2026-09-08 23:51부터 2026-09-09 00시대 KST에 기준 `fb256bc`에서 진행했다.
첫 사이클의 브라우저 중단 보존이 검사 묶음 내부까지 적용되는지, 수동 CLI의
계획과 예산이 양립하는지, 네이티브 진단이 실행 한계를 지키는지 확인했다.

## 확인한 문제와 수정

| 문제 | 수정 전 실제 관찰 | 수정 후 |
| --- | --- | --- |
| 같은 검사 묶음의 뒤쪽 예외가 앞쪽 실패를 지움 | 검색 결과 실패를 만든 뒤 count 노드를 읽다가 예외 발생. 16개 모두 `not-run`이 되어 실패 소실 | 완료된 개별 관찰을 페이지 밖으로 즉시 전달. 같은 입력에서 1 fail / 15 not-run, 오류·종료 1 유지 |
| 수집 통로가 아직 시작하지 않은 검사 기록도 받음 | 위 수정의 중간 구현에 시작 시점 payload를 넣으면 관찰하지 않은 ordinary-save가 pass로 남음 | 활성 묶음 ID만 허용하고 종료/예외 시 해제. 초기 문서가 없으면 16개 모두 `not-run` |
| 실행 전에 알 수 있는 예산 모순을 허용 | 6회가 필요한 계획을 한도 5로, 8회가 필요한 계획을 한도 6으로 생성한 뒤 실행 기록 제출에서야 `incomplete` | 계획 검증 후 후보 디렉터리 생성 전에 최소 실행 수 검사. 초과 시 종료 2와 후보·활성 포인터 보존 |

브라우저 수정은 검색·일반 저장의 두 배치에만 선택적 완료 콜백을 추가했다.
기존 직접 호출의 반환 구조, history 검사의 잠정 상태, suite 버전과 16개
행동 기준은 유지한다. 수집 JSON 형식·미확정 상태·중복·다른 묶음 기록도
오류로 보존하며 이 검사를 적대적인 페이지의 진위 인증으로 해석하지 않는다.

계획 예산은 각 대상/전이 쌍에 baseline과 candidate가 하나씩 필요한 계약을
따른다. 초기화의 양수 예산 허용이나 제출된 초과 실행의 `incomplete` 판정은
바꾸지 않았다. 실행 수·시간의 누적 강제나 모델 자동 실행은 추가하지 않았다.

## 새 과업의 지침 관찰

별도 새 문맥에서 `ui-slop-audit`를 직접 읽고 합성 Compose 프로필 화면을
진단했다. 소스의 `finally`가 실패에도 성공·닫기를 수행하고, 실패 처리에서
입력을 초기값으로 덮으며, 저장 중 추가 입력은 클릭 시점 요청에 포함되지
않는다는 세 발견을 부모가 소스와 대조했다. 기존 카드·브랜드·필드 순서를
유지하는 좁은 수정 제안과 아직 실행하지 않은 확인 방법을 구분했다.

읽기 전용 과업의 TASK/DESIGN/Kotlin은 전후 해시가 같았다. 스킬 snapshot의
65개 파일도 `fb256bc`와 일치했다. 최종 해시가 중간 쓰기 부재를 증명하지는
않는다. Android SDK·빌드 프로젝트·기기가 없고 실제 표시·닫기·영속 저장은
검증하지 않았다. 부모 검토는 작성자와 별도 문맥의 AI 검토이며 맹검은 아니다.

현재 지침이 이 요청을 처리했으므로 새 범용 규칙은 추가하지 않았다.
`skill-creator`의 실제 실패 중심 원칙에 따라 도구 결함과 지침 결함을 구분했다.
이는 단일 정적 진단이며 반복·버전 비교·일반적인 스킬 품질 향상 근거가 아니다.

## 최종 검증

- `python3 -B -m unittest discover -s tests -q`: 261개 중 브라우저 전용 41개를 건너뛰고 220개 통과.
- `AI_SLOP_BROWSER_TESTS=1 python3 -m unittest discover -s tests -p test_browser_checks.py -v`: 최종 29개 통과. 동일 배치 예외·실제 문서 이동의 7개 하위 시나리오와 잘못된 수집 기록·초기화 전 기록을 포함한다.
- `AI_SLOP_BROWSER_TESTS=1 python3 -m unittest discover -s tests -p test_scope_browser_checks.py -v`: 공유 수집기 변경 후 12개 통과. 그 뒤 이 공유 파일은 바뀌지 않았다.
- `npm test`: 기본 Python 3.9.6에서 8개 통과. 이번 사이클은 Python 3.12 npm 검사를 다시 실행하지 않았다.
- `npm run check`, `npm run check:js`, `git diff --check`: 배포 해시 75개, 스킬 7개·정적 사례 계약 24개, 링크·의존성·구문·공백 검사 통과.
- `PYTHONPATH=tests python3 -B -m unittest test_local_learning.LocalLearningLifecycleTests.test_proposal_run_budget_matches_all_planned_baseline_candidate_runs -v`: 부모 재검증에서 네 하위 조건 통과. 동일 검사에 기준 snapshot CLI를 지정하면 두 초과 조건이 실패한다.
- 부모가 압축용 최종 고정 브라우저 도구로 원본 중단 사례를 별도 실행해 0 pass / 1 fail / 15 not-run, 수집 오류 1개와 종료 1을 확인했다.
- 별도 읽기 전용 최종 코드 검토에서 추가 조치가 필요한 결함은 발견하지 못했다. 이 검토는 테스트 재실행이 아니다.
- 기록 디렉터리에서 `shasum -a 256 -c SHA256SUMS`: 두 사이클의 압축 해시 모두 통과.
- 별도 검토자가 압축을 새 임시 경로에 해제해 정확히 121개 일반 파일의 목록·크기·SHA-256 일치를 확인했다. 고정 도구 재실행에서도 브라우저 전후 0/0/16 → 0/1/15와 양쪽 수집 오류 1개·종료 1을 재현했고, 압축 안 CLI의 네 예산 하위 조건도 통과했다.

[고정 자료 압축](cycle-2.tar.gz)과 [파일별 해시](cycle-2-inventory.json)를 보존한다.
압축의 `EVIDENCE.md`에 각 실행의 범위·전후 자료·재현 명령과 네이티브 검토를
담았다. 포함된 스크린샷으로 이 사이클의 화면 품질 통과를 판정하지 않았다.
공식 `quick_validate.py`는 첫 사이클에서 확인한 PyYAML 부재가 그대로여서
다시 실행하지 않았다. 원격 CI·Windows/Linux·호스트 자동 발견은 미검증이다.

## 남은 검토와 다음 사이클

수동 CLI의 합성 흐름에서 같은 후보에 rejected 보고서와 별도의 eligible
보고서를 남기고 후자를 명시해 채택하는 동작도 관찰했다. 현재 판정 범위는
지정 보고서이며 보고서 사이의 전체 실패 이력을 합산하지 않는다. 합법적인
입력 정정·완료 후 재평가와 불리한 시도의 숨김을 구분하는 계약이 필요하므로
이번 예산 수정에 임의의 영구 거부 정책을 끼워 넣지 않았다.

밤샘 목표는 계속 활성 상태다. 다음 사이클에서는 다른 실제 요청의 결과와
보존 경계를 평가하고, 새 규칙이 필요한 실패가 있는지 확인한다. 테스트나
문서의 양을 늘리는 일을 스킬 개선 성과로 세지 않는다.
