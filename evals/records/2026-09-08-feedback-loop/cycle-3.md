# 세 번째 피드백 사이클

2026-09-09 00시대 KST, 기준 `1fe742d`에서 문구·화면 과업을 별도 새 문맥으로
시험했다. 이 과정에서 포커스 잘림을 전체 페이지 캡처가 가리는 문제를 찾아
수집기를 수정했다. 제품 과업의 결과와 도구 수정의 효과를 구분한다.

## 과업 결과

### 저장·CSV 문구

`ux-writing` 실행은 한국어 locale의 지정 값 9개만 수정했다. 클라우드·다른
기기 저장 약속과 실제 완료되지 않은 다운로드 안내를, 브라우저 임시 저장과
CSV 링크 준비로 바로잡았다. 진행 중의 완료 단정, 예상 시간, 확인되지 않은
실패 원인·로그인·관리자 권한 요구도 제거하고 실제 재시도 행동을 안내했다.

부모의 최종 범위 검사에서 키·문자열별 변수와 다른 파일은 보존됐다. 원본과
결과 모두 별도 상태/데이터 단언 20개가 통과했다. 원본의 잘못된 문구도 이
단언은 통과하므로 문구 정확성은 자동 통과 수로 판단하지 않았다. 부모가
소스·실제 상태별 문자열·접근 가능한 행동 이름·320px 실패/파일 준비 이미지를
대조해 좁은 문구 개선을 확인했다. 링크는 누르지 않았고 Blob 바이트만 읽었다.
기기 다운로드 완료·실물 기기·스크린리더는 미검증이다.

### 주문 비교 밀도

`ui-visual-refine` 실행은 compare.css의 padding-block 16→8px와 DESIGN의
허용된 예외 구역만 변경했다. 브랜드·열·행 행동·기본 화면을 유지하며 부모의
기존 두 행동 검사는 통과했다. 넓은 화면의 비교 행 밀도 개선도 확인했다.

그러나 전체 보존 통과는 아니다. 글자를 CSS로 2배 확대한 320×800에서는
행을 Tab으로 선택하고 Enter를 누른 뒤 결과물의 오른쪽 포커스가 잘렸고,
동일 조건의 원본은 온전히 보였다. 320×864에서는 반대로 원본이 잘리고
결과물은 보였다. 원래 레이아웃의 스크롤바 메커니즘이 있다는 사실과 이번
수정이 특정 동일 조건에서 회귀를 드러냈다는 사실을 함께 기록한다.

작성자가 현상을 발견한 뒤 부모는 비교 조건을 혼합하지 않도록 피드백했고,
최종 보고서에 이 회귀를 명시했다. 표 수평 휠 이동으로 복구됐지만 키보드만의
복구를 증명하지 않는다. 임의의 다른 padding으로 한 높이만 통과시키거나,
허용되지 않은 공통 CSS·행 로직 수정으로 과업을 확대하지 않았다. 이 결과를
회귀 없는 품질 향상으로 채택하지 않는다.

두 실행의 스킬 snapshot은 각각 65개 파일로 기준 커밋과 일치했다. 새 문맥에
TASK·원본·스킬만 제공한 `snapshot-direct`이며 버전 비교·반복·호스트 자동
발견은 아니다. 추가 스킬 규칙이 필요한 실패 근거와 제품/평가 도구의 결함을
구분하는 `skill-creator` 원칙을 적용했고 공통 스킬 지침은 늘리지 않았다.

## 확인한 캡처 결함과 수정

부모가 포커스 치수와 PNG를 대조하자 전체 페이지 이미지에서 잘림이 보이지
않았다. 별도 검토자가 같은 상태를 viewport→full-page→viewport 순서로
찍어 재현했다. 문제 조건의 치수는 같고 첫/끝 viewport 이미지 해시도 같지만
full-page만 오른쪽 외곽선을 온전하게 그렸다. 다른 조건에서는 full-page 촬영
직후 표 scrollLeft 자체가 달라지기도 했다. Chrome 내부 원인은 단정하지 않는다.

공통 helper에 선택적인 captureBeyondViewport 인자를 추가하고 두 드라이버의
keyboard.png만 false로 지정했다. 기본 전체 페이지 overview는 호환성을 위해
유지한다. 이는 포커스 증거의 프레임을 보존하는 수정이며 모든 overview 부작용,
제품 포커스 문제·모든 브라우저·접근성 적합성을 해결하거나 인증하지 않는다.

새 테스트는 실제 PNG 헤더에서 키보드 이미지의 375×844 크기와 더 긴 overview
유지를 확인한다. 원래 검색 이미지는 375×1100, scope 이미지는 375×1332여서
두 테스트가 실패했고, 수정 후 둘 다 통과했다. 이 크기 검사는 전체 픽셀의
의미를 자동 판정하지 않는다. 확인한 픽셀 차이는 별도의 재현·이미지 검토다.

## 검증

- `python3 -B -m unittest discover -s tests -q`: 263개 중 브라우저 전용 43개를 건너뛰고 220개 통과.
- `AI_SLOP_BROWSER_TESTS=1 python3 -m unittest discover -s tests -p test_browser_checks.py -v`: 30개 통과.
- `AI_SLOP_BROWSER_TESTS=1 python3 -m unittest discover -s tests -p test_scope_browser_checks.py -v`: 13개 통과. 두 브라우저 suite는 최종 수집기에서 병렬 실행했다.
- `npm test`: 기본 Python 3.9.6에서 8개 통과. 이번 사이클은 다른 Python 버전의 npm 검사를 다시 실행하지 않았다.
- `npm run check`, `npm run check:js`, `git diff --check`: 배포 해시 75개·스킬 7개·정적 사례 계약 24개·링크·의존성·구문·공백 검사 통과.
- 부모 source 검사: 문구의 지정 값 9개와 각 보간 변수, 밀도의 CSS 한 값과 DESIGN 예외 구역만 변경된 것을 확인했다. 최종 바이트 비교는 중간 쓰기 부재를 인증하지 않는다.
- 부모 문구 상태/데이터 검사: 원본 20 pass / 결과 20 pass, 수집 오류 각각 0개. 작성자 자체 9개 검사 묶음은 별도 자료로 두고 합산하지 않았다.
- 부모 포커스 관찰: 원본/결과 × 800/864px의 네 조건을 같은 글자 확대·키 순서로 재현했다. 최종 viewport PNG와 촬영 직후 치수를 함께 확인했다.
- 압축용 고정 도구에서 새 Chrome 회귀 두 개를 다시 실행했다. before-tools는 두 PNG 높이에서 실패, final-tools는 두 검사 통과였다. 이식한 연속 캡처 helper도 종료 0·예외 0으로 같은 치수와 scrollLeft 변화를 재현했다.
- 최초 압축의 독립 검토에서 macOS tar가 파일 목록 밖의 AppleDouble 메타데이터 532개를 추가한 것을 발견했다. 원래 자료는 유지하고 `COPYFILE_DISABLE=1 tar -czf ...`로 다시 압축했다. 처음 압축은 임시 경로에 별도 보존하고 최종 해시에는 교정된 압축만 사용한다.
- 교정된 압축의 독립 검토에서 tar 자체와 해제한 폴더 모두 정확히 405개 일반 파일의 경로·크기·SHA-256이 일치했다. 추가·중복·위험 경로·특수 파일은 없었다. 별도 경로의 문구 재실행은 전후 각각 20개 통과, 포커스 재실행은 같은 네 조건의 결과를 재현했고, 최종 도구의 두 Chrome 회귀도 통과했다. 재실행 뒤 해제한 입력 바이트도 동일했다.
- 기록 디렉터리에서 `shasum -a 256 -c SHA256SUMS`: 세 압축 해시 모두 통과. 별도 읽기 전용 최종 코드 검토에서도 추가 수정이 필요한 결함은 발견하지 못했다.

[압축](cycle-3.tar.gz)과 [파일별 해시](cycle-3-inventory.json)에 TASK·원본/결과·
snapshot·부모/작성자 자료·캡처 재현·수정 전후 도구와 회귀 자료를 보존한다.
압축의 EVIDENCE.md에 재현 명령과 자료별 한계를 기록했다. 작성자 helper의
당시 절대 경로와 원문 보고를 보존했으며 부모 helper는 압축 해제 후 재실행할
수 있다. 브라우저 프로필·캐시는 포함하지 않는다.

시각 작성자의 Chrome 로그에 GCM·updater 관련 출력이 있어 실행 플래그만으로
백그라운드 네트워크와 전역 자동 동작을 모두 차단했다고 주장하지 않는다.
명시적 외부 게시·PR·설치는 수행하지 않았다. 공식 quick_validate.py는 기존
PyYAML 부재로 다시 실행하지 않았고 스킬 진입점 변경도 없다.

밤샘 목표는 계속 활성 상태다. 다음 사이클에서도 통과 숫자만으로 개선을
판정하지 않고 실제 요청의 결과, 미해결 회귀와 증거의 신뢰성을 함께 확인한다.
