# 네 번째 피드백 사이클

2026-09-09 01시대 KST. 기준 `a3daf5c`에서 수집 중단 보고와 압축 기록의
검증을 개선했다. 이번 사이클은 평가 도구의 합성 회귀 검사이며 새 제품 과업,
스킬 버전 비교나 일반적인 학습 효과의 증거로 세지 않는다.

## 중단 보고의 누락

독립 진단에서 scope 종료 코드 0은 “결과를 기록했다”는 명시된 규약임을
확인했다. 이를 구현 실수로 바꾸지 않고 그대로 유지했다. 실제 문제는 개별
관찰에서 잡은 오류가 전체 `observations.collectionErrors`에 빠지는 것이었다.
초기 HTTP 503뿐 아니라 간격 실패를 관찰한 뒤 reload HTTP 503이 발생해도
목록이 비어 있었다. 이제 앞서 기록한 `fail`과 부분 사실은 유지하면서 오류를
관찰 ID와 함께 집계한다.

검색 검사기에도 같은 누락이 있었다. 공유 URL 이동 실패, 신뢰된 popstate
관찰의 timeout, 실패 뒤 상태 읽기 예외가 종료 0을 반환했다. 검색의 기존
“수집 완료” 규약에 맞춰 이제 오류 목록과 종료 1에 반영한다. 나중의 독립
검사는 계속 실행한다. 실제 신뢰된 이벤트가 엉뚱한 history 항목에 도착하거나
상태가 틀린 것은 일반적인 행동 실패이며, 그 자체를 수집 오류로 세지 않는다.
기존 수집 결과의 검사 schema·판정 기준·수동 평가 함수 반환형은 보존했다.

수정 전 회귀 단언 다섯 개가 실패하고 반대 사례 하나는 통과했다. 수정 후
같은 여섯 검사가 모두 통과했다. 별도 검토자가 원래 HTTP 장애 주입을 제품
수정 없이 다시 실행했고, 다섯 조건 모두 기존 checks 배열과 제품·소스
inventory가 일치했다. 초기/후속 503의 전체 오류 목록만 필요한 대로 보강됐다.
scope 호출은 정상·일반 실패·수집 중단 모두 종료 0이라는 호환성을 유지했다.
검색 호출자는 이전에 잘못 반환된 0 대신 1을 받을 수 있으므로 오류 종료여도
browser.json을 보존하고 읽어야 한다.

## 기록 검증과 과거 자료의 한계

새 `scripts/check_evidence_archive.py`는 압축을 풀거나 수정하지 않고 inventory와
정확한 일반 파일 집합·크기·SHA-256을 대조한다. 기존 두 inventory 형식과
일반 디렉터리 헤더를 허용하고 추가·누락·변경·중복·위험 경로·링크·특수 파일,
tar 종료부와 검출된 압축 오류를 거부한다. 결과는 JSON이며 검증 통과 0,
잘못되거나 읽을 수 없는 입력 1, 잘못된 CLI 사용 2를 반환한다.

이 도구로 이전 기록을 다시 검사하자 다음이 드러났다. 세 압축과 inventory의
검사 전후 바이트·크기·해시는 모두 동일하며 원본을 다시 쓰지 않았다.

| 기존 압축 | 새 검증 결과 |
| --- | --- |
| flow | 목록의 77개 해시는 일치하지만 추가 일반 파일 159개가 있어 거부. AppleDouble 136개 외에 목록 밖 자료 23개도 포함 |
| cycle-2 | 목록의 121개 해시는 일치하지만 추가 AppleDouble 175개가 있어 거부 |
| cycle-3 교정본 | 일반 파일 405개·5,120,548바이트가 정확히 일치해 통과 |

이전의 “목록에 있는 파일 일치”나 macOS에서 해제된 파일 검증은 raw tar의
정확한 전체 파일 집합 검증과 다르다. 그 한계를 여기서 보완하며 원래 시험의
관찰 결과가 조작됐다거나 과거 압축 바이트가 바뀌었다는 뜻은 아니다. 세 번째
사이클의 교정 전 임시 압축도 추가 AppleDouble 532개 때문에 새 도구가 거부했다.
과거 압축과 공개한 해시는 유지하고 새 기록에만 교정된 작성 절차를 적용한다.

독립 검토에서 비정상적으로 큰 tar 메타데이터 크기가 JSON 대신 traceback을
내는 경우를 찾아 오류 처리를 보강했다. 또한 bzip2/xz reader가 압축 stream
밖의 뒤따르는 바이트를 무시할 수 있어, 논리 파일 검증과 전체 압축 SHA-256을
구분하도록 문서에 명시했다. 일반 보안 감사나 증거의 진위 보증으로 넓히지 않는다.

## 최종 검증

- `python3 -B -m unittest discover -s tests -q`: 290개 중 브라우저 전용 46개를 건너뛰고 244개 통과. 최종 압축 검증기 24개 검사도 포함한다.
- `AI_SLOP_BROWSER_TESTS=1 python3 -B -m unittest discover -s tests -p test_browser_checks.py -v`: 32개 통과. 같은 방식의 `test_scope_browser_checks.py`는 14개 통과했다.
- 부모의 여섯 대상 Chrome 검사: 수정 전 다섯 실패·반대 사례 하나 통과, 수정 후 여섯 통과. 별도 독립 HTTP 503 재현 다섯 조건과 이를 이식한 부모 helper 재실행도 종료 0·제품 보존을 확인했다.
- 거대한 메타데이터 헤더 세 종류의 새 오류 처리 검사는 수정 전 traceback 때문에 세 하위 조건이 실패했고, 수정 후 모두 JSON invalid·종료 1·빈 stderr였다. 링크·특수 파일·중복·손상·추가 파일 등의 거부와 입력 불변도 전용 검사에 포함했다.
- `npm test`: 기본 Python 3.9.6에서 8개 통과. `npm run check`, `npm run check:js`, `git diff --check`도 배포 해시 75개·스킬 7개·정적 사례 계약 24개·링크·의존성·구문·공백 검사 통과. 다른 Python 버전의 npm 검사는 이번에 반복하지 않았다.
- 새 압축 초안은 일반 파일 349개가 목록과 일치했지만 독립 재실행에서 scope 테스트의 `summarize_scope_trials` import 누락을 발견했다. 검색 네 검사는 통과했으나 scope 두 검사는 시작하지 못했다. 수정 전후 snapshot에 변경 없는 해당 의존성을 추가하고 실패 로그를 보존해 다시 묶었다. `COPYFILE_DISABLE=1`로 만든 교정본은 일반 파일 353개·2,532,105바이트의 정확한 경로·크기·해시가 일치했다. 초안 압축과 inventory는 별도 임시 경로에 보존했다.
- `/opt/homebrew/bin/python3.12 -B -m unittest discover -s tests -p test_evidence_archive.py -v`: 기존 Python 3.12.14에서도 압축 검증기 24개 통과. 기록 디렉터리의 `shasum -a 256 -c SHA256SUMS`는 과거 세 개와 새 압축 모두 통과했다. 전체 압축 해시 일치는 앞에서 밝힌 두 과거 inventory의 불완전성을 없애지 않는다.
- 부모가 저장소가 아닌 분리된 `before-tools/`에서 같은 여섯 Chrome 검사를 다시 실행해 다섯 실패·반대 사례 하나 통과를 재현했다. 즉 누락된 import를 보완한 뒤에는 시작 오류가 아니라 의도한 수정 전 관찰 단언에서 실패했다.
- 교정 압축을 독립 검토자가 새 경로에 풀어 압축 자체와 해제한 353개 파일·94개 일반 디렉터리 헤더를 검증했다. 압축 안의 검증기 24개와 최종 Chrome 대상 6개가 모두 통과했으며 재실행 전후 inventory도 같았다. 수집기·검증기·테스트가 저장소와 일치하고 전후 도구 차이는 두 수집기뿐임을 확인했다. 남은 수정 필요 지적은 없었다.
